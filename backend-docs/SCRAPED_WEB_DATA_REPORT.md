# AeroPulse Integrated Scraped-Web Data Report

**Snapshot date:** 2026-10-15
**Scope:** read-only inventory of scraper/parser code, related persistence models and documentation, in-project data files, and the local database file. No web requests, scraper commands, external systems, or database writes were performed.

## Executive summary

The backend contains two manual HTML scraping/import paths: a GlobalMilitary.net Indian Air Force aircraft-inventory parser and a Bharat-Rakshak flying-squadron index parser. Their code and target source URLs are present, and Django models can persist parsed snapshots/reference records. The only local database found, `backend/db.sqlite3`, is zero bytes and uninitialized. Therefore **no actual imported scraped rows or their collection times can be verified in this project snapshot**. No raw downloaded HTML file was found in the inspected repository tree.

The CSVs under `backend/data/fabricated/` are explicitly generated synthetic/fabricated demo data, not scraped web data. Neither those fixtures nor the scraped reference schemas establish facility-specific parts stock, flight hours to an airbase, facility capacity, or current maintenance availability.

## Scraper behavior and persistence

### GlobalMilitary inventory

`parse_iaf_inventory()` in `backend/fleet/globalmilitary.py` parses page text for an optional `Updated DD Mon YYYY` date and aggregate active/on-order totals, locates the “Indian Air Force” section and its next table, and normalizes rows into the fields persisted by `ExternalFleetAircraft`. Missing markers become `None`; the parser raises if the expected heading/table or aircraft rows are absent. `scrape_iaf_fleet` uses `requests.get` with a timeout, then creates an `ExternalFleetSnapshot` and its child rows inside `transaction.atomic()`.

`ExternalFleetSnapshot` stores source URL/name, optional source update date, retrieval timestamp, and optional aggregate counts. `ExternalFleetAircraft` stores category/name/origin/model year/count changes/order totals. The model relation is a source snapshot, not an individual `fleet.Aircraft` identity mapping. The API view may expose the latest stored snapshot, but it cannot supply time-specific base capacity or aircraft routing.

### Bharat-Rakshak squadron index

`parse_iaf_squadrons()` in `backend/squadron/bharat_rakshak.py` parses the “Flying Units” section and stops at “Missile Units”; it keeps links with names ending Squadron/Sqn and de-duplicates names case-insensitively. It derives an ID from the normalized name and SHA-1 digest. The management command fetches the source, supports `--dry-run`, and otherwise upserts by `squadron_id`, recording `source_url` and a local synchronization timestamp. This establishes what the importer intends to ingest, not the source's correctness or completeness.

`Squadron` fields include `squadron_id`, `name`, optional/reference `base`, optional aircraft count/type, operational role, source URL, and last-sync timestamp. The command updates name, role, URL, and sync time, while source-provided base/count are not available from the index according to the backend documentation. `SquadronAircraft` is not populated by this scraper and has no FK to `fleet.Aircraft`.

Neither pipeline runs on a schedule in the inspected code. Both are explicit management commands that fetch current HTML when manually invoked. The GlobalMilitary snapshot retains a source-side update date when parsed and always records retrieval time. Bharat-Rakshak records local sync time, but parser output has no source-side update timestamp or coverage/completeness contract. No raw HTML, source response hash, or immutable source snapshot is persisted by either command.

## Reliability and limitations

- Public HTML can change structure; parser guards detect some missing/empty structure but do not authenticate the content or verify all records were represented.
- No current scrape rows or collection timestamps can be counted in the empty local DB. No cross-source identifier reconciliation was performed or established.
- GlobalMilitary records are type/category totals, not aircraft-level rows. `source_updated_on` is optional.
- Bharat-Rakshak derived squadron identifiers depend on the displayed name; renames can produce changed IDs. Its source timestamp and coverage are absent.
- Fabricated CSV dates, aircraft identifiers, inventory values, fault history and labels are generated data. Their realistic appearance does not establish provenance or operational accuracy.
- `ml/configs/facilities.yaml` contains only scoring weights. `rank_facilities()` accepts caller-supplied location, facility status, capacity, backlog, parts and duration values; its status/backlog/capacity inputs are not tied to a time interval, source provenance, or live reservations. Its heuristic ranking is not availability evidence.
- No scraped source can prove real-time inventory, facility opening, a free 72-hour window, or operational suitability.
- Data licensing and redistribution permissions were not established; no conclusion of permission is made.

## Minimum safe future use

For the isolated synthetic scheduler, provide explicit, clearly named synthetic fixture values for (1) required part IDs and quantities available at each fixture base, (2) flight hours to each base, (3) complete base occupancy intervals keyed to an explicit fleet identifier, and (4) snapshot observation, coverage, expiry, and completeness metadata. These fixtures must remain in tests/development and be labelled `SYNTHETIC — NON-OPERATIONAL`.

Before operational use, do not derive the above values from scraped counts or global stock. An accountable owner must identify sources that map AeroPulse work-order/fleet/base/part IDs, prove coverage over every candidate interval, supply freshness and completeness guarantees, and expose changes/cancellations. Normalize and validate those source contracts before treating any value as operational evidence. No such live integration is implemented here.
